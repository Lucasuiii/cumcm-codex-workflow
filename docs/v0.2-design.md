# CUMCM Codex Workflow v0.2 Design Draft

Status: accepted implementation specification. The v0.2 core described here is
implemented; deferred items remain explicitly labeled.

## 1. Product decision

Version 0.2 should turn the current staged scaffold into an evidence-carrying
competition workflow. Its primary invariant is:

```text
official source
  -> problem fact
  -> task capability
  -> model responsibility
  -> executable evidence
  -> result
  -> paper claim or figure
```

Every important result, figure, and claim must traverse this chain. Missing
links are visible workflow failures rather than gaps that the paper-writing
stage may silently fill.

The workflow remains Codex-native and file-backed. It does not attempt to be a
general autonomous research agent, a replacement for mathematical judgment,
or a certificate that a submitted model is correct.

## 2. Design decisions

### 2.1 Keep one orchestrator Skill

Retain one concise `cumcm-workflow` entrypoint. The entrypoint selects the
active stage, loads only that stage's reference, and invokes deterministic
validators. Detailed contracts belong in `references/` and `schemas/`; repeated
checks belong in `scripts/`.

Do not split the workflow into many large, overlapping Skills. Separate Skills
would increase routing ambiguity, duplicate invariants, and make cross-stage
state harder to reason about.

### 2.2 Preserve the seven top-level stages

Version 0.2 keeps the v0.1 stage identifiers:

1. `intake`
2. `problem-analysis`
3. `model-design`
4. `computation`
5. `validation`
6. `paper`
7. `delivery`

New capabilities are stage-owned artifacts and gates, not additional
top-level stages. This preserves state-file compatibility while still allowing
each subproblem to progress and rerun independently.

### 2.3 Separate lifecycle, evidence, and review states

These three concepts must not share one overloaded `status` field.

- Stage lifecycle: `not_started`, `in_progress`, `awaiting_review`, `passed`,
  `needs_revision`, or `blocked`.
- Evidence state: `not_checked`, `missing_evidence`,
  `supported_not_reproduced`, `reproduced`, `partially_supported`,
  `contradicted`, `ambiguous`, or `not_applicable`.
- Human review: a review record containing reviewer label, time, scope,
  decision, and optional notes.

A structurally valid JSON file cannot set a human review decision by itself.

### 2.4 Use stable identifiers rather than prose matching

Cross-artifact links use explicit IDs. Recommended forms are:

| Entity | Example |
|---|---|
| source | `SRC-001` |
| fact | `FACT-Q1-001` |
| capability | `CAP-Q1-001` |
| model component | `MODEL-Q1-001` |
| run | `RUN-Q1-20260830T120000Z` |
| result | `RES-Q1-001` |
| claim | `CLM-Q1-001` |
| figure | `FIG-Q1-001` |

IDs are immutable after another artifact references them. Human-readable text
may change without breaking the evidence graph.

### 2.5 Treat machine checks as typed evidence

Validators report what they established:

- `structural`: schema, path, identifier, hash, or relationship checks;
- `execution`: a recorded command ran and produced preserved outputs;
- `numerical`: assertions, residuals, independent calculations, or
  cross-solver agreement;
- `semantic`: human or explicitly scoped reviewer judgment;
- `visual`: rendered paper or figure inspection.

No validator may emit a generic message that implies mathematical correctness.

## 3. Proposed project layout

The following is the canonical v0.2 project layout generated or managed by the
Skill. Not every file is required at project creation.

```text
project/
|-- .cumcm/
|   |-- state.json
|   `-- validation-report.json
|-- problem/
|   |-- official/                 immutable copied inputs
|   `-- SOURCE_MANIFEST.json
|-- analysis/
|   |-- PROBLEM_FACTS.json
|   `-- TASK_CAPABILITIES.json
|-- model/
|   |-- MODEL_CONTRACT.json
|   `-- CROSS_QUESTION_LEDGER.json
|-- code/
|-- runs/
|   `-- <run-id>/
|       |-- RUN_MANIFEST.json
|       |-- stdout.log
|       |-- stderr.log
|       `-- outputs/
|-- results/
|   `-- RESULTS_INDEX.json
|-- validation/
|   |-- CLAIM_LEDGER.json
|   `-- reviews/
|-- figures/
|   `-- FIGURE_MANIFEST.json
|-- paper/
|-- delivery/
|   `-- DELIVERY_MANIFEST.json
`-- environment/
    |-- README.txt                human-readable reproduction notes
    `-- environment.json          runtime and dependency metadata
```

Original files are copied into `problem/official/` and never edited. Generated
or converted files live outside that directory and identify their parent
source.

## 4. Common artifact envelope

Each v0.2 contract uses a common envelope:

```json
{
  "schema_version": "0.2.0",
  "artifact_type": "problem_facts",
  "project_id": "2026-CUMCM-B",
  "updated_at": "2026-08-30T12:00:00Z",
  "producer": {
    "kind": "human | codex | script | external_tool",
    "name": "...",
    "version": "..."
  },
  "review": {
    "decision": "unreviewed | accepted | revision_requested",
    "reviewer": null,
    "reviewed_at": null,
    "scope": null,
    "notes": null
  }
}
```

`updated_at` records serialization time, not evidence time. Executions,
measurements, and reviews carry their own timestamps.

## 5. Artifact contracts

### 5.1 `problem/SOURCE_MANIFEST.json`

Owns the identity and provenance of every official or externally acquired
input.

Required per source:

- `source_id`;
- relative `path`;
- `sha256`, byte size, and media type;
- `origin`: `official`, `organizer_attachment`, `external_reference`, or
  `team_created`;
- acquisition description and, when applicable, URL;
- `authoritative_for`: the facts or fields for which this source is primary;
- `derived_from` for OCR, conversions, or cleaned tables;
- `mutable`: false for copied official inputs.

Passing this contract proves identity and inventory completeness only when the
expected source list has been independently reviewed.

### 5.2 `analysis/PROBLEM_FACTS.json`

Separates objective problem facts from interpretation.

Required sections:

- `subproblems`: exact requests and expected output types;
- `facts`: statement, source ID, page or location, raw value, normalized value,
  unit, and applicability;
- `definitions`: symbols and official terminology;
- `ambiguities`: competing readings and their evidence;
- `assumptions`: team-added assumptions, rationale, affected capabilities, and
  sensitivity obligation.

OCR text may populate candidates but cannot be the final authority for formulas
or ambiguous tables without rendered-page inspection.

### 5.3 `analysis/TASK_CAPABILITIES.json`

This is the central planning contract. Each capability describes what the
solution must actually do, not which buzzword should appear in code.

Required per capability:

- `capability_id` and `subproblem_id`;
- objective and required output;
- referenced fact IDs;
- required inputs and their source IDs;
- acceptance checks;
- owner model-component IDs;
- expected code entry points;
- expected result IDs;
- downstream claim or figure IDs when known;
- lifecycle state and blocking issues.

Coverage is complete only when every requested subproblem output is owned by at
least one accepted capability and every capability has an observable acceptance
check.

### 5.4 `model/MODEL_CONTRACT.json`

Defines the mathematical responsibility and scope of each model component.

Required per component:

- decision variables, states, parameters, and units;
- inputs and outputs;
- equations or formulation reference;
- objective and constraint families;
- feasible set or policy class;
- stochastic assumptions and dependence structure;
- estimation, optimization, or solution method;
- approximation and discretization choices;
- identifiability or optimality scope;
- failure conditions and fallback method;
- owned capability IDs;
- planned verification evidence.

Strong words such as global optimum, unbiased, equivalent, robust, or causal
must be declared as proposed claims with explicit certificate requirements.

### 5.5 `model/CROSS_QUESTION_LEDGER.json`

Makes reuse between subproblems explicit.

Required per shared item:

- canonical name and ID;
- producer subproblem or source;
- consumer subproblems;
- definition, unit, coordinate system, time basis, and index convention;
- transformation rule;
- uncertainty propagation rule when relevant;
- authoritative artifact and conflict resolution status.

The ledger must reject silent reuse of the same symbol with incompatible units,
populations, time windows, or optimization scope.

### 5.6 `runs/<run-id>/RUN_MANIFEST.json`

Records one actual execution in an immutable run directory.

Required fields:

- run ID, purpose, subproblem, and capability IDs;
- exact argument vector and working directory;
- start and finish times, exit code, and completion state;
- source revision or code-file hashes;
- input paths, evidence roles, and hashes when required;
- runtime, operating system, interpreter, package, and solver metadata;
- random generator and seeds when stochastic;
- stdout and stderr paths;
- output paths, evidence roles, hashes when required, byte sizes, and media types;
- assertions executed and their outcomes;
- parent run when this is a retry or derivative run.

`completed` means the process exited as recorded. It does not mean the model is
correct or the result is acceptable.

Use hashes selectively: official inputs, formal run inputs, claim-bearing
machine-readable outputs, and frozen delivery files are blocking. Prefer a Git
commit or source revision for code identity. Figure drift during paper editing
and byte-size mismatches are warnings; final figures are frozen by listing them
in the delivery manifest. Logs, caches, temporary files, and LaTeX auxiliary
files do not need hashes. Digest recording and comparison are automated, so no
human review of the hash string itself is required.

Run file records declare `evidence_role`. Inputs use `formal_input` or
`auxiliary_input`; outputs use `claim_bearing_output`, `intermediate_output`,
or `diagnostic_output`. Only the two evidence-bearing roles require hashes, and
every indexed result must point to a `claim_bearing_output` declared by its run.
Older v0.2 records without a role retain strict behavior: inputs default to
`formal_input` and outputs to `claim_bearing_output`.

### 5.7 `results/RESULTS_INDEX.json`

Is the only source from which the paper stage may introduce numerical results.

Required per result:

- result ID and semantic name;
- value or path to a structured value;
- unit, precision, and display rounding;
- run ID and exact output locator;
- applicable subproblem, scenario, population, and parameter scope;
- uncertainty or tolerance when relevant;
- validation checks and evidence state;
- superseded result ID when replaced.

The unrounded stored value remains authoritative. Paper formatting may round it
but must not recompute or alter it.

### 5.8 `validation/CLAIM_LEDGER.json`

Tracks high-bearing statements, including negative and limitation claims.

Required per claim:

- claim ID, text, type, and intended paper location;
- scope and qualifiers;
- supporting fact, model, run, result, and figure IDs;
- evidence state;
- contradiction or ambiguity notes;
- required certificate for strong claims;
- reviewer record.

Claims with `missing_evidence`, `contradicted`, or `ambiguous` cannot be written
as established conclusions. `supported_not_reproduced` must not be shortened to
`reproduced` in prose.

### 5.9 `figures/FIGURE_MANIFEST.json`

Required per figure or table:

- figure ID, kind, and purpose;
- generating script or manual provenance;
- source result IDs and run IDs;
- output path and hash;
- axes, units, transformations, filters, and aggregation definitions;
- randomness and seed if used;
- caption claims;
- paper location;
- visual review status.

Decorative diagrams may omit run IDs but must declare `kind: conceptual` and
must not visually imply measured quantities.

### 5.10 `delivery/DELIVERY_MANIFEST.json`

Required fields:

- selected profile;
- final files with relative path, role, hash, and byte size;
- compile command, engine, exit code, log path, warnings summary, and page count;
- unresolved warnings and accepted exceptions;
- environment and reproduction notes;
- excluded sensitive or non-submission files;
- final human review record.

The manifest verifies the delivered bytes. It does not certify that the contest
submission portal received those bytes.

## 6. Stage gates and rollback

| Stage | Required artifacts | Machine gate | Human gate |
|---|---|---|---|
| `intake` | source manifest | identity, hash, path, expected-source coverage | confirm official input set |
| `problem-analysis` | facts, capabilities | source links, unit fields, subproblem coverage | approve interpretation and assumptions |
| `model-design` | model contract, cross-question ledger | ownership, scope, variable and dependency completeness | choose model and claim scope |
| `computation` | run manifests, result index | actual outputs, hashes, environment, assertions | accept completed run set |
| `validation` | claim ledger, validation report | evidence graph, numerical and cross-question checks | approve supported claims and limitations |
| `paper` | manuscript, figure manifest | only indexed numbers, figure provenance, claim linkage | approve content and presentation |
| `delivery` | delivery manifest, compiled files | compile, hashes, required files, unresolved warning policy | approve submission package |

When a validator finds a conflict, it reports the earliest owning stage. The
workflow sets that stage to `needs_revision` and later dependent stages to
`blocked`; it does not delete their artifacts. After correction, only affected
runs, results, claims, figures, and paper sections need to be rebuilt.

Examples:

- wrong official unit -> return to `problem-analysis`;
- model constraint missing in code -> return to `model-design` or
  `computation`, depending on ownership;
- result copied from an unrecorded run -> return to `computation`;
- paper overstates a supported result -> return to `paper`;
- figure uses the wrong result ID -> return to `validation` or `paper` after
  checking whether the underlying number is wrong.

## 7. Validator architecture

### 7.1 Implemented scripts

```text
scripts/
|-- cumcm_check.py
|-- workflow_checks.py
|-- migrate_v01.py
|-- inventory_artifacts.py
`-- legacy v0.1 validators
```

`cumcm_check.py` is a dispatcher, not a second workflow engine.
`workflow_checks.py` consolidates cross-contract logic so rule IDs and evidence
semantics do not drift between shallow wrappers. The dispatcher runs the
checks required for a selected stage or profile and writes
`.cumcm/validation-report.json`.

Implemented interface:

```text
python scripts/cumcm_check.py --project <path> --stage validation --profile strict
python scripts/cumcm_check.py --project <path> --all --profile sprint
```

### 7.2 Diagnostic contract

Every finding has:

- stable rule ID, for example `CLAIM-E003`;
- severity: `error`, `warning`, or `info`;
- evidence type;
- owning stage;
- artifact path and JSON pointer when available;
- concise message;
- related IDs;
- remediation hint that does not fabricate missing evidence.

Exit codes:

- `0`: no errors;
- `1`: one or more validation errors;
- `2`: invalid invocation, unreadable contract, or validator failure.

A warning never silently upgrades evidence. Profiles may change whether a
documented optional check is required, but they may not demote factual,
execution, contradiction, or claim-trace errors.

### 7.3 Meaningful checks

Prefer checks tied to observable behavior:

- execute unit and invariant tests;
- evaluate residuals and conservation relations;
- compare independent derivations or solvers;
- verify stochastic reproducibility from recorded seeds;
- perturb assumptions or parameters when robustness is claimed;
- confirm optimization certificates and their declared feasible set;
- trace exact output locations rather than matching numbers in prose;
- render and inspect equations, tables, figures, and final PDF pages.

Keyword occurrence, file existence, a solver success flag, or a polished
validation report is structural evidence only.

## 8. Profiles

Profiles control breadth and polish, not truth requirements.

| Requirement | `strict` | `sprint` |
|---|---|---|
| official-source inventory | required | required |
| fact and capability review | required | required |
| model scope and assumptions | full | concise but required |
| real execution evidence | required | required |
| cross-question consistency | required | required |
| result and claim traceability | required | required |
| independent logic pass | required | required |
| alternative-model comparison | required when decision-relevant | may be recorded as deferred |
| extended sensitivity analysis | required for robustness claims | only claim-critical checks |
| optional explanatory figures | encouraged | omitted |
| typographic polish | full pass | submission-safety pass |
| unresolved error | blocks | blocks |

An independent logic pass means a separate review pass with the solution's
conclusions withheld as far as practical. It may use a fresh Codex task, a
different model, or a human reviewer. Same-model review remains correlated and
must not be presented as independent proof.

## 9. Always-prohibited shortcuts

- Generate or select data because it makes the proposed method win.
- Claim global optimality outside the explicitly searched or certified class.
- Treat non-rejection as equivalence or lack of evidence as evidence of no
  effect.
- Use a successful solver status as proof that the mathematical formulation is
  faithful.
- Create new numerical results while writing the paper.
- Copy a displayed number into the paper without a result ID.
- Hide incompatible runs or silently overwrite an earlier run directory.
- Set minimum page, figure, table, or model counts as quality requirements.
- Advance a human gate from an automated validator.

## 10. Migration from v0.1

### 10.1 Compatibility rules

- Keep the Skill name and seven stage identifiers.
- Add `workflow_version: "0.2.0"` to `.cumcm/state.json`.
- Preserve existing v0.1 artifacts until migrated; never rewrite them in place
  without a backup or version-control history.
- Map `TASK_CONTRACT.json` to `TASK_CAPABILITIES.json` through an explicit
  migration report.
- Map old claim status `supported` to `supported_not_reproduced`, never to
  `reproduced`.
- Treat absent v0.2 fields as migration warnings during a transition period,
  not as inferred values.
- Refuse mixed-project IDs or ambiguous artifact ownership.

### 10.2 Implementation sequence

1. Add schemas and fixtures without changing current validators. Complete.
2. Add the common diagnostic format and dispatcher. Complete.
3. Implement source, fact, capability, and state migration checks. Complete.
4. Implement model, cross-question, run, and result checks. Complete.
5. Implement claim, figure, and delivery checks. Complete; arbitrary prose
   tracing remains deliberately contract-driven rather than regex-inferred.
6. Update stage references and `SKILL.md` only after their validators exist.
   Complete.
7. Migrate the regression example and compare v0.1 versus v0.2 diagnostics.
   Complete through executable synthetic tests.
8. Remove compatibility aliases only in a later breaking release. Deferred.

## 11. Regression and acceptance plan

### 11.1 Core regression scenario

Use the CUMCM 2024 B policy-scope issue as the first semantic regression:
enumerating a fixed homogeneous policy class must not support a claim of global
optimality over history-dependent feedback policies. The fixture should include
both the overclaim and the corrected scoped claim.

### 11.2 Implemented negative fixtures

- official source hash changes after intake;
- a fact cites an unregistered source;
- a subproblem request has no capability owner;
- a capability names code that never executes;
- code output exists but has no run manifest;
- two subproblems reuse a symbol with different units;
- a result points to an output with a mismatched hash;
- a robustness claim has no perturbation evidence;
- a figure is generated from an unindexed result;
- the delivery PDF differs from its recorded hash;
- Sprint mode attempts to demote a claim-trace error.

Arbitrary-number scanning in free-form paper prose is deliberately not a
machine fixture: regex matches would create false confidence. The paper review
must instead confirm deliberate use of result and claim IDs. A future
instrumented LaTeX result macro may make that check deterministic.

### 11.3 v0.2 acceptance criteria

Version 0.2 is ready for release only when:

- all schemas validate positive fixtures and reject targeted negative fixtures;
- every validator emits stable diagnostics and documented exit codes;
- a project can resume from every stage without chat history;
- run directories and stable IDs allow an affected subproblem to rerun without
  overwriting unrelated runs;
- the complete claim graph resolves through IDs rather than prose matching;
- Strict and Sprint produce identical results for non-negotiable errors;
- the regression suite demonstrates at least one caught mathematical-scope
  overclaim, not only malformed JSON;
- the Skill passes the Codex quick validator;
- provenance and limitations documents describe the evidence boundary plainly.

## 12. Deferred work

- Automatic `model-xray` invocation remains deferred. v0.2 should expose a
  stable export hook from claim, run, result, figure, and delivery manifests.
- Multi-model orchestration is optional and must not be a correctness claim.
- Portal submission automation is out of scope.
- Contest-specific model libraries are out of scope until the core evidence
  contracts work on at least two materially different problems.
- A graphical dashboard is unnecessary for v0.2; machine-readable diagnostics
  and a concise Markdown summary are sufficient.

## 13. Proposed implementation milestones

### M1: Contract foundation

Deliver the common envelope, eleven contract JSON Schemas, fixtures, state versioning, and
migration report format.

### M2: Vertical evidence chain

Deliver capability, model-to-code, run, result, and claim linkage checks. This
is the minimum milestone that materially improves v0.1.

### M3: Consistency and review

Deliver cross-question, numerical, strong-claim, and figure checks, plus
contract-driven paper-trace and independent-review guidance. Free-form prose
scanning remains deferred.

### M4: Profiles and resumability

Deliver the dispatcher, Strict/Sprint policy, stage rollback, localized rerun,
and consolidated validation report.

### M5: Competition regression

Migrate the CUMCM 2024 B example, add negative fixtures, and run behavioral
acceptance tests.

### M6: Delivery readiness

Finish compile and delivery checks, provenance review, public documentation,
and release readiness assessment.

## 14. Recommended first implementation slice

Implement M1 and the following M2 path before expanding breadth:

```text
TASK_CAPABILITIES
  -> MODEL_CONTRACT
  -> RUN_MANIFEST
  -> RESULTS_INDEX
  -> CLAIM_LEDGER
```

This slice tests the defining v0.2 idea. If it cannot reliably expose an
unsupported or over-scoped claim, adding more stages, models, or presentation
features would only create a more polished version of the v0.1 scaffold.
