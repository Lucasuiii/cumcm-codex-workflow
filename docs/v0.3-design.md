# v0.3 paper-quality design

> Historical document. The current v0.4 contract is described in [v0.4-design.md](v0.4-design.md); v0.3 projects are not accepted by the current Skill.

Version 0.3 is the complete, standalone contract for the seven-stage workflow. It treats evidence traceability and paper quality as related but distinct obligations: a paper must both cite inspectable evidence and present a complete contest-ready argument.

## What the new contracts establish

`PAPER_PLAN.json` requires each validated claim to have a planned evidence route and each subproblem to cover interpretation, boundaries, variables, objective/constraints, derivation, algorithm, results, validation, and limitations. It records why each figure exists. Reference papers guide transferable reasoning practices, not fixed page or figure targets.

`PAPER_QUALITY_REPORT.json` separates content review from rendered-PDF layout review and binds both to exact bytes. `paper_status` distinguishes `technical_draft`, `candidate`, and `final`. A final paper needs accepted content, layout, and final QA, full rendered-page coverage, and no open P0 issue.

`PAPER_REVISION_LOG.json` starts with a preserved snapshot and records only quality-triggered rounds. Each round identifies input/output bytes, issue IDs, changed locations, and verification. The workflow does not require an arbitrary number of revisions.

`LATEX_TEMPLATE_MANIFEST.json` binds the modular paper source tree to the project, maps every official subproblem to a generated section, records the intended engine, and lists placeholder markers. `main.tex` only assembles modules. The bundled generic CTeX scaffold does not claim official compliance; delivery requires a human comparison with the rules and package for the current competition year.

`COMPILE_RECEIPT.json` stores argument arrays, engine/version, attempts, logs, warning scans, page counts, font/glyph results, diagnostics, and the selected PDF. It binds that PDF to the exact paper quality report and reconciles it with the delivery manifest.

`.cumcm/decisions.jsonl` makes human decisions append-only and artifact-bound. `record_decision.py` calculates hashes; reviewers confirm visible artifacts and summaries rather than manually checking digests. A changed artifact makes the latest accepted decision stale until a new review is recorded.

## Gate modes

- `preflight`: returns zero when all automated checks pass and only explicit human decisions remain; the report says `gate_status=awaiting_review`.
- `enforce`: requires automated checks and applicable human gates to pass.

Both modes block evidence, execution, schema, hash, claim, content/layout, compile, hash-chain, and stale-decision failures.

## Version boundary

The validator accepts only `schema_version: "0.3.0"` and `workflow_version: "0.3.0"`. Older project layouts require an explicit, separately reviewed reconstruction into the current contracts; this repository does not contain an automatic migration path and never infers missing evidence.
