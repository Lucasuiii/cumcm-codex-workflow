# v0.4 独立复核与读者导向论文设计

> 历史设计。当前 contract 见 [v0.5](v0.5-design.md)；已有 v0.4 workspace 使用[迁移说明](migration-v0.4-to-v0.5.md)。

v0.4 是七阶段工作流的独立 contract，不是 v0.3 compatibility layer。旧 project 必须明确重建到 v0.4 contract，缺失证据不会被推断。

## Validation 前的 Independent Review

`build_independent_review_package.py` 创建一个尽量不包含原结论的复核包，包括官方输入、题目和模型 contract、计算入口、run record 与 executed output，并附带小型 Reviewer Skill 和结构化结果模板。

原任务在打包后停止，由用户选择人工或模型 reviewer，并记录单独的 task ref。同一对话 review 不能通过；同模型 fresh task 明确标记为 correlated，不同模型或人工可标记为 independent。这些标签都不能把 review 变成数学证明。

Raw review 原样保存在 `INDEPENDENT_REVIEW_RAW.md`；`INDEPENDENT_REVIEW_RESULT.json` 记录 reviewer、范围、finding 和 verdict。严重缺陷返回最早受影响阶段。缺少用户提供的官方材料时结果为 inconclusive，不授权自动网络搜索。

## 面向评委的论文与内部 Sidecar

最终论文写给评委，而不是工作流引擎。内部 ID、evidence-state enum、本机路径、run coverage 和 gate 术语保存在 `PAPER_TRACEABILITY.json` 等 JSON sidecar 中。`paper_visible_text_check.py` 提取 PDF 文本并阻止已知元数据泄漏；过度小数精度和数字过密句子作为 review flag。

`PAPER_PLAN.json` 增加 reader narrative，并把完整 evidence route 留在可见正文之外。Content review 检查机理解释、推导、结果含义、数字表达、摘要综合、结论直接性和参考风格迁移。同一上下文的 content review 或 final QA 不能 finalize 论文。

`cumcm-contest-ctex` scaffold 是模块化、按问题生成的，默认不插入目录。每问从任务解释和机理推进到模型、算法、结果解释、验证和局限。用户提供当年规则或官方模板并记录 compliance review 前，scaffold 始终保持 submission-neutral。

## Delivery 边界

Delivery 要求三个可单独定位的角色：

1. 精确的已审阅 final PDF；
2. 带入口和必要资产的 editable LaTeX source；
3. 带入口和 rerun 说明的 computation source。

Compliance check 只使用用户提供的官方材料。如果缺少规则或模板，delivery 必须报告 blocked 并向用户索取。提交动作仍由用户控制。

## 精简 Digest 政策

仅在字节身份确实重要时保留 SHA-256：

- 改变后会影响题意的官方来源；
- formal computation input 与 claim-bearing output；
- explicit approval 覆盖的少量 stage contract；
- paper QA 和 delivery 实际审阅的 PDF。

Decision event 追加记录但不建立 hash chain。普通代码、LaTeX、文档、编辑期图件、compile log、cache、temp 和支持文件不要求 digest。可选 digest stale 通常只是 warning；人审查可见产物和摘要，不需要核对 64 位字符串。

## 证据边界

Schema、token lint、成功执行和 accepted review 只能建立工作流证据，不能证明题意理解、数学建模、实现、统计有效性或全局最优性。Strong claim 仍需要 claim-specific certificate 和真实执行证据。
